# Workspace-Set Manifest Generation — The Layer-2 Discovery Contract

## Purpose

Defines how AI-DWG generates `workspace-set-manifest.yaml` — the **Layer-2 authoritative index of ALL Layer-3 per-team workspaces** in a multi-workspace generation. It is the multi-workspace analog of `workspace-manifest.yaml`, but it is a **Layer-2 control-plane artifact** (owned by the architects/owners in the design workspace) — it never lives inside an L3 workspace. It is what makes the whole set discoverable and governable **from Layer 2**.

**Output:** `{project_root}/{slug}-management/workspace-set-manifest.yaml` (the L2 control plane).

**Condition:** Generate IF `workspaceTopology ∈ {per-team, hybrid}` (Config Gate Q4). SKIP for `single` (no set to index).

**Cluster:** Multi-workspace (Layer-2 control plane). Runs after per-team partitioning + per-member generation.

> **Layer discipline (LAYERED_TOPOLOGY §1.1):** this manifest + the contract registry + the roll-up all live in the **Layer-2 control plane**; the L3 per-team workspaces are generated and pushed down. L2 reads L3 status *down* for control; L3 never reaches up. The set-manifest sits **above** the per-member `.governance/workspace-manifest.yaml` files, never inside one.

## MANDATORY: Stage Sub-Role — Team Topology Architect + Automation Engineer

Team Topology Architect (`#persona-subrole-team-topology-architect` — owns the set's team/interaction intent) layered with Automation Engineer (machine-readable contract). ADDS a dimension — does NOT replace the primary role.

### Behavioral Shifts
- The set-manifest is an API for the whole set — stable keys, machine-parseable, no prose.
- Every member entry must resolve to a real generated L3 workspace (folder path, or repo URL when polyrepo).
- Record the interaction modes + contract ownership so cross-workspace governance (GCE) and the human architect can see the whole set from one place.

### Anti-Patterns
- Do NOT place this manifest inside an L3 workspace — it is an L2 control-plane artifact.
- Do NOT list a member that was not generated.
- Do NOT hand-maintain — regenerate from the actual member set + the team-context-registry every time.

## workspace-set-manifest.yaml Schema

```yaml
# {slug}-management/workspace-set-manifest.yaml  (LAYER 2 control plane)
# Generated by AI-DWG — DO NOT EDIT MANUALLY
---
dwgVersion: v1.2
projectId: PRJ-{ABBREV}-{YYYY}-{NNN}
layer: 2                             # this manifest + registry + roll-up all live in the L2 control plane
workspaceTopology: per-team          # single | per-team | hybrid
physicalLayout: subfolder            # subfolder | polyrepo
l3WorkspacesRoot: ../{slug}-workspaces/
contractRegistry: contracts/         # AUTHORITATIVE, here in L2 (read-only copies pushed down to each L3 ws)
generatedOn: {ISO-timestamp}
members:
  - team: {team-1}
    teamType: stream-aligned         # stream-aligned | platform | enabling | complicated-subsystem
    workspace: ../{slug}-workspaces/{team-1}/     # L3 dev workspace (or a git URL when polyrepo)
    manifest:  ../{slug}-workspaces/{team-1}/.governance/workspace-manifest.yaml
    ownsContexts: [{BC-slug}]
    ownsServices:  [{SVC-slug}]
    publishesContracts: [contracts/{svc-a}/openapi.yaml]      # owns these in the L2 registry
    consumesContracts:  [contracts/{svc-b}/openapi.yaml@^1.2]
    interactions:
      - with: {team-2}
        mode: x-as-a-service         # collaboration | x-as-a-service | facilitating
  - team: {platform}
    teamType: platform
    workspace: ../{slug}-workspaces/{platform}/
    provides: [contracts/platform/*]
---
```

## Generation Rules

### Rule 1: Derive Members From the Registry + Partition
Each `members[]` entry is one team from the partition (`mapping/team-workspace-partitioning.md`), sourced from the AP `team-context-registry.md` (authoritative) or the CODEOWNERS/MS-01 fallback. One member per team — never per service.

### Rule 2: DWG is Sole Writer
Header says `DO NOT EDIT MANUALLY`. Only DWG writes it (same custodianship as the per-member manifest). GCE/TGE/FLO/DFE + the human architect read it.

### Rule 3: physicalLayout Drives the `workspace` Value
`subfolder` → relative folder path (`../{slug}-workspaces/{team}/`). `polyrepo` → the member's git repo URL. Consumers resolve each member's governance home through this field (path vs URL) — the ONLY thing that varies by layout.

### Rule 4: Record Ownership + Interactions
`ownsContexts`/`ownsServices` = the team's `BC-*`/`SVC-*`; `publishes`/`consumes` = its contracts in the L2 registry (pinned versions on consumes); `interactions` = the named interaction modes (TT-03) from the Team Topology Map.

### Rule 5: Regenerate on Delta
On Mode-2 reconciliation (team boundary or contract change), regenerate the set-manifest + re-baseline only the affected members.

## Consumer Contract (How Downstream Reads It — all Layer-2, or L2 reading L3 down)

| Consumer | Reads | For |
|----------|-------|-----|
| **AI-GCE** | `members[].workspace`/`manifest`, `interactions`, `contractRegistry` | Cross-workspace GOV-TT roll-up; iterate members via one discovery contract (mode-transparent) |
| **AI-TGE** | `members[]`, `contractRegistry` | Contract + integration testing across the set |
| **AI-FLO** | `members[]`, `projectId` | Portfolio roll-up across the set |
| **AI-DFE** | `members[]` | Reads the set *down* for the cross-lifecycle view |
| **Human architect/owner** | whole file + `WORKSPACE_SET_CONTEXT_MAP.md` | Single-pane control of the set from L2 |

Each L3 workspace keeps its own single-workspace `.governance/workspace-manifest.yaml` for *intra*-workspace discovery; this L2 set-manifest sits **above** them.
